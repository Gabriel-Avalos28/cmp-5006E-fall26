1. [CRITICAL] SQL Injection in do_login: `user` and `pw` are put straight into the SQL string with an f-string and no parameters. An input like `' OR '1'='1` skips the login check and returns every row, including the admin's secret.
2. [HIGH] Reflected XSS in do_reflect: the `name` query parameter goes into the HTML response as-is, with no escaping, and is served as text/html. An attacker can craft a `/?name=<script>...</script>` link that runs script in the victim's browser.
3. [HIGH] Command Injection in do_ping: the `host` value is joined into a shell command (`ping -c 1 {host}`) with no checks or quoting. This copy only echoes the command, but any real `os.system` call would let shell metacharacters (`;`, `|`, `` ` ``, `$()`) run any command.
4. [MEDIUM] Information Disclosure in do_login: when the database raises an error, the response includes the raw error message and the full SQL query text. This helps an attacker tune SQL injection payloads and learn the schema.
5. [MEDIUM] Sensitive Data Exposure in do_login: a successful login sends back the `secret` column for every matching row instead of just a success flag or session token. Any login, legitimate or injected, leaks secret data.
6. [MEDIUM] Plaintext Password Storage in make_db: user passwords are stored and compared in cleartext instead of with a slow salted hash (bcrypt, scrypt or argon2). Any read of the database exposes every password.
7. [MEDIUM] Hardcoded Credentials in make_db: the account `admin/s3cr3t` and weak passwords such as `alice/password` are written into the source code, so anyone who reads the code can log in.
8. [LOW] Hardcoded Secret in make_db: the CANARY_SECRET value is a literal in the source and is seeded into the database, so it is exposed to anyone with the source.
9. [MEDIUM] Missing Rate Limiting in do_POST: the `/login` endpoint has no rate limiting, lockout or delay. Brute-forcing and credential stuffing go unchecked.
10. [LOW] Denial of Service / Unbounded Input in _form: the Content-Length header is trusted with no upper limit, so a client can make the server read a huge body into memory. A negative Content-Length makes `rfile.read(-1)` wait for EOF, which ties up a worker thread.
11. [LOW] Improper Input Validation in _form: a body that is not valid UTF-8 raises an exception the code does not catch. Valid JSON that is not an object (for example a list) makes `form.get` crash in do_POST. Either case can be used to cause server errors.
12. [LOW] Missing CSRF Protection in do_POST: the state-checking POST endpoints accept form-encoded bodies with no CSRF token or Origin check, so another site can submit cross-site requests to them.
13. [LOW] Missing Security Headers in _send: responses have no Content-Security-Policy, X-Content-Type-Options, X-Frame-Options or charset. This leaves out defense-in-depth against XSS, content sniffing and clickjacking.
14. [LOW] Cleartext Transmission in main: the server speaks plain HTTP with no TLS, so login credentials and leaked secrets cross the network unencrypted.
15. [LOW] Insecure Network Binding in main: the server listens on 0.0.0.0, which exposes this deliberately vulnerable app on every network interface instead of only localhost.
